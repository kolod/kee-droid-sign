# Feature Specification: Core Signing Modules

**Feature Branch**: `001-core-signing-modules`

**Created**: 2026-10-08

**Status**: Draft

**Input**: User description: "Build the module(s) that do the core work: generate passwords;
generate keys and a *.jks file; authenticate with GitHub; add or update secrets in a repository;
produce the certificate fingerprint for the Android Developer Console in a format like
B2:71:2B:B7:0A:51:E6:85:B1:CB:29:C4:75:05:87:89:48:24:60:1F:CB:F7:32:EA:E2:F1:E7:EA:24:CE:CC;
create tests for these modules." (original request was written in Ukrainian; translated per
Constitution Principle I)

## Scope Note

This feature delivers the **core, UI-independent capabilities** of the plugin (Constitution
Principle VI). The Tools-menu window and the Options tab that expose these capabilities to the
end user are separate features and are out of scope here. The "users" of this feature are
therefore the plugin's UI layer and, ultimately, the developer operating it; every capability
MUST be usable and verifiable without any user interface.

## Clarifications

### Session 2026-10-08

- Reference CI usage provided by the user: the workflow decodes
  `secrets.ANDROID_KEYSTORE_BASE64` with `base64 -d` into `app/release.keystore.jks`, then writes
  `storePassword`, `keyAlias`, `keyPassword` from `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`,
  `ANDROID_KEY_PASSWORD` into `app/keystore.properties` via an unquoted heredoc.
- Q: Which characters may generated passwords contain, given they pass through an unquoted
  heredoc and a `.properties` file? → A: Shell/properties-unsafe characters (`$`, backtick,
  backslash, quotes, whitespace) are always excluded, not configurable; symbols come only from
  the safe set `!#%+,-./:=?@^_~`.
- Q: Should keys be generated by the external JDK key tool or inside the plugin? → A: Inside the
  plugin process; no Java required, no key material ever written to temporary files.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Generate strong passwords (Priority: P1)

A developer preparing a new Android signing key needs strong, random passwords for the keystore
and the key. The core generates passwords that meet configurable rules (length and character
classes) so the developer never has to invent one.

**Why this priority**: Every other capability (keystore creation, secret export) depends on
having credentials; it is also the simplest, fully self-contained slice.

**Independent Test**: Request passwords with various rules and verify length, character-class
coverage, and that repeated requests do not produce duplicates.

**Acceptance Scenarios**:

1. **Given** default rules, **When** a password is requested, **Then** a password of the default
   length is returned containing at least one character from each enabled character class.
2. **Given** rules with length 40 and only letters and digits enabled, **When** a password is
   requested, **Then** the result is exactly 40 characters and contains only letters and digits.
3. **Given** rules that cannot be satisfied (e.g. length shorter than the number of required
   classes, or no class enabled), **When** a password is requested, **Then** the request is
   rejected with a clear error explaining the conflict.
4. **Given** any rules, **When** 10,000 passwords are generated, **Then** none contains `$`,
   backtick, backslash, a quote, or whitespace, and every symbol is from the safe set.

---

### User Story 2 - Generate a signing key and keystore file (Priority: P1)

The developer provides an alias, the certificate owner details (name, organization, country,
etc.), a validity period, and passwords. The core produces a Java KeyStore (`.jks`) file
containing a new private key and its self-signed certificate, suitable for signing Android apps.

**Why this priority**: The keystore is the central artifact the whole plugin exists to manage.

**Independent Test**: Generate a keystore with known inputs, then reopen it with the given
passwords and verify the alias, key algorithm/size, certificate subject, and validity dates.

**Acceptance Scenarios**:

1. **Given** valid alias, owner details, validity and passwords, **When** key generation is
   requested, **Then** a `.jks` keystore is produced that opens with the store password and
   contains exactly one private-key entry under the given alias, readable with the key password.
2. **Given** a successful generation, **When** the certificate is inspected, **Then** its subject
   matches the owner details and its validity end date is at least the requested number of years
   in the future.
3. **Given** a machine without any Java runtime, **When** generation is requested, **Then** it
   succeeds — key generation needs no external tools.
4. **Given** generation succeeds, fails or is cancelled midway, **When** the operation ends,
   **Then** no file containing key material has been written to disk (unless the caller
   explicitly asked for an output file).

---

### User Story 3 - Produce the certificate fingerprint for the Developer Console (Priority: P2)

The developer needs to paste the certificate fingerprint of the signing key into the
Android Developer Console. The core computes the fingerprint from a keystore (or
certificate) and formats it as uppercase hexadecimal byte pairs separated by colons, e.g.
`B2:71:2B:B7:...:CC`.

**Why this priority**: Needed to register the key with Google, but only after a key exists.

**Independent Test**: Compute the fingerprint of a known test certificate and compare it with
the expected reference value.

**Acceptance Scenarios**:

1. **Given** a keystore, its password and alias, **When** the fingerprint is requested, **Then**
   the SHA-256 fingerprint of the alias's certificate is returned as 32 uppercase hex byte pairs
   joined by `:`.
2. **Given** the SHA-1 variant is requested, **When** the fingerprint is computed, **Then** 20
   byte pairs are returned in the same format.
3. **Given** a wrong password or unknown alias, **When** the fingerprint is requested, **Then**
   a clear error is returned and no partial value is produced.

---

### User Story 4 - Authenticate with GitHub (Priority: P2)

To export secrets, the developer must grant the plugin access to their GitHub account. The core
establishes an authenticated GitHub session, verifies it, and reports which account is signed in
and whether it has permission to manage secrets of a given repository.

**Why this priority**: Prerequisite for secret export; independent of key generation.

**Independent Test**: Authenticate against GitHub (or a simulated GitHub service in automated
tests) and verify the reported account name and repository permission check.

**Acceptance Scenarios**:

1. **Given** valid credentials, **When** authentication is performed, **Then** the core reports
   success and the GitHub login name of the authenticated account.
2. **Given** invalid, expired or revoked credentials, **When** authentication is performed,
   **Then** a clear "authentication failed" result is returned without exposing the credential.
3. **Given** an authenticated session and a repository `owner/name`, **When** access is checked,
   **Then** the core reports whether the account may manage that repository's Actions secrets.
4. **Given** authentication succeeds, **When** the credential needs to be kept for later use,
   **Then** it is handed back to the caller for storage in the KeePass database and is never
   written to plugin settings, logs or disk.

Authentication method: the user supplies a GitHub personal access token (fine-grained token
recommended, with read/write permission for repository Actions secrets; classic tokens with
`repo` scope are also accepted). OAuth device flow is out of scope for this feature and may be
added later.

---

### User Story 5 - Add or update repository secrets (Priority: P2)

The developer selects a GitHub repository and the core uploads the keystore (encoded as text) and
its credentials (store password, key alias, key password) as GitHub Actions secrets, creating
missing secrets and updating existing ones, so CI workflows can sign release builds.

**Why this priority**: Delivers the CI integration value; depends on Stories 2 and 4.

**Independent Test**: Upload a set of secrets to a simulated GitHub service and verify that each
was sent encrypted with that repository's public key, using the expected names, and that the
result reports created vs. updated per secret.

**Acceptance Scenarios**:

1. **Given** an authenticated session and a repository without these secrets, **When** export is
   requested, **Then** all secrets are created and the result lists each as "created".
2. **Given** some secrets already exist, **When** export is requested, **Then** the core reports
   which secrets would be overwritten before writing, and after the caller confirms, updates them
   and lists them as "updated".
3. **Given** custom secret names are supplied, **When** export runs, **Then** the custom names are
   used instead of the defaults.
4. **Given** the network fails or GitHub rejects one secret, **When** export runs, **Then** the
   result reports per-secret success or failure and the error reason; no secret value appears in
   the error.
5. **Given** any export, **When** data is transmitted, **Then** secret values are only ever sent
   encrypted with the repository's public key.

---

### User Story 6 - Automated test suite (Priority: P1)

The project maintainer can run an automated test suite that verifies every core module without a
real GitHub account, network access, or user interface.

**Why this priority**: Explicitly requested and required by Constitution Principle VI for
security-critical logic.

**Independent Test**: Run the test suite on a clean machine without network access; all tests
pass.

**Acceptance Scenarios**:

1. **Given** the test suite, **When** it is run offline, **Then** all tests for password
   generation, keystore generation, fingerprint formatting, GitHub authentication and secret
   export pass, with GitHub interactions simulated.
2. **Given** a JDK is installed on the test machine, **When** the suite runs, **Then** an
   optional interoperability test confirms the JDK key tool opens the generated keystore; without
   a JDK that single test is reported as skipped with a reason.

---

### Edge Cases

- Alias or owner details containing characters that are special in certificate subject names
  (commas, quotes, `=`, non-ASCII letters) must be escaped correctly or rejected with a clear
  message.
- Target keystore file already exists: generation must not overwrite it silently.
- Passwords shorter than the minimum accepted by the keystore format (6 characters) are rejected.
- Repository does not exist, is archived, or the account lacks admin/secrets permission.
- GitHub API rate limit reached or token missing a required scope.
- Keystore larger than the maximum GitHub secret size (48 KB) after text encoding.
- Secret names that violate GitHub naming rules (must start with a letter or `_`, only
  alphanumerics and `_`, must not start with `GITHUB_`).
- Cancellation requested while key generation or a network call is running.

## Requirements *(mandatory)*

### Functional Requirements

**Password generation**

- **FR-001**: The core MUST generate passwords using a cryptographically secure random source.
- **FR-002**: Password rules MUST be configurable: length (default 32, allowed 8–128) and
  character classes (uppercase, lowercase, digits, symbols), each enabled by default. The symbols
  class is restricted to the CI-safe set `!#%+,-./:=?@^_~`.
- **FR-003**: Every generated password MUST contain at least one character of each enabled class.
- **FR-004**: Generated passwords MUST NEVER contain `$`, backtick, backslash, double quote,
  single quote, or whitespace; this exclusion is not configurable. Rationale: passwords are
  substituted into an unquoted shell heredoc and a Java `.properties` file in CI (see
  Clarifications), where these characters would be expanded or treated as escapes. Excluding
  visually ambiguous characters (e.g. `0/O`, `1/l/I`) MAY be offered as an additional option.
- **FR-005**: Unsatisfiable rules MUST be rejected with a descriptive error.

**Key and keystore generation**

- **FR-006**: The core MUST generate a key pair and self-signed certificate and write them into a
  keystore file in JKS format under a caller-specified alias.
- **FR-007**: Default key parameters MUST be RSA 4096-bit with SHA-256-based signature and a
  validity of 30 years; algorithm size and validity MUST be overridable by the caller.
- **FR-008**: The certificate subject MUST be built from caller-provided owner fields (common
  name, organizational unit, organization, locality, state, country code); at least the common
  name is required.
- **FR-009**: The core MUST accept separate store and key passwords.
- **FR-010**: The core MUST return the generated keystore content to the caller (for storage in
  the KeePass database) and MUST NOT write key material to disk at any point (including temporary
  files), unless the caller explicitly requests an output file path; an existing file at that
  path MUST NOT be overwritten.
- **FR-011**: Key and keystore generation MUST be performed entirely within the plugin process,
  without requiring Java or any other external tool.
- **FR-012**: The generated keystore MUST be readable by the standard JDK key tool and by Android
  build tooling (verified by the optional interoperability test).

**Certificate fingerprint**

- **FR-013**: The core MUST compute the SHA-256 fingerprint of a certificate taken from a
  keystore (given password and alias) or from a standalone certificate.
- **FR-014**: The fingerprint MUST be formatted as uppercase two-digit hexadecimal byte values
  separated by `:` with no leading/trailing separators.
- **FR-015**: The core SHOULD also provide the SHA-1 fingerprint in the same format, since some
  Google services still request it.

**GitHub authentication**

- **FR-016**: The core MUST authenticate with GitHub using a user-supplied personal access token
  and report the authenticated login name.
- **FR-017**: The core MUST validate a stored credential on demand and report "valid",
  "invalid/expired", or "insufficient permissions".
- **FR-018**: The core MUST check whether the authenticated account can manage Actions secrets
  of a given repository.
- **FR-019**: Credentials MUST be returned to the caller for storage in the KeePass database and
  MUST NOT be persisted, logged, or included in error messages by the core.
- **FR-020**: All communication with GitHub MUST use HTTPS.

**Repository secrets**

- **FR-021**: The core MUST list which of the target secret names already exist in a repository.
- **FR-022**: The core MUST create or update repository Actions secrets, encrypting each value
  with the repository's public key before transmission.
- **FR-023**: The default secret set MUST be: `ANDROID_KEYSTORE_BASE64` (keystore file encoded as
  standard single-line Base64 without line breaks, decodable with `base64 -d`), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`; every
  name MUST be overridable by the caller.
- **FR-024**: Secret names MUST be validated against GitHub naming rules before any upload.
- **FR-025**: Overwriting existing secrets MUST require an explicit confirmation flag from the
  caller; without it, the core reports the conflicts and writes nothing.
- **FR-026**: The export result MUST report, per secret, created / updated / failed with reason.

**Cross-cutting**

- **FR-027**: All core modules MUST be usable without any user interface and MUST support
  cancellation of long-running operations.
- **FR-028**: No core module MAY write secret values (passwords, keys, tokens) to logs, exception
  messages, or settings.
- **FR-029**: An automated test suite MUST cover every functional area above; GitHub interaction
  MUST be testable against a simulated service without network access.

### Key Entities

- **PasswordPolicy**: Length, enabled character classes, exclusion options.
- **KeyRequest**: Alias, owner details (certificate subject fields), key algorithm and size,
  validity in years, store password, key password.
- **SigningKeystore**: Generated keystore content, alias, certificate, format (JKS); the unit
  stored in the KeePass database.
- **CertificateFingerprint**: Digest algorithm (SHA-256 / SHA-1) and formatted value.
- **GitHubCredential**: Secret credential plus the authenticated login name; stored only in the
  KeePass database.
- **RepositoryTarget**: Repository owner and name.
- **SecretMapping**: Secret name → value source (keystore, store password, alias, key password).
- **ExportResult**: Per-secret outcome (created / updated / failed) and reason.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of generated keystores can be reopened with the supplied passwords and used to
  sign an Android release build without further conversion.
- **SC-002**: Fingerprints produced by the core match a reference value for the same certificate
  in 100% of test cases.
- **SC-003**: A complete flow — generate passwords, generate keystore, compute fingerprint —
  finishes in under 30 seconds on a typical developer workstation.
- **SC-004**: Exporting the default four secrets to a repository finishes in under 15 seconds on
  a normal internet connection.
- **SC-005**: After any operation (successful, failed, or cancelled), zero files containing key
  material or passwords remain in temporary locations.
- **SC-006**: The automated test suite runs fully offline and covers every functional
  requirement group (password, keystore, fingerprint, authentication, secrets).
- **SC-007**: Across the test suite, no log output or error message contains any secret value.

## Assumptions

- The provided example fingerprint (31 byte pairs) is a truncated sample of a SHA-256 certificate
  fingerprint, which has 32 byte pairs; SHA-256 is treated as the primary format.
- The fingerprint is the value the Android Developer Console requests when registering an app and
  its signing certificate (Constitution Principle IV, item 3). Producing an encrypted private-key
  upload for Google Play App Signing (PEPK) is out of scope for the project.
- No Java runtime or other external tool is required by this feature (decided 2026-10-08 during
  planning: in-process generation keeps key material off disk). A JDK is used only by one
  optional interoperability test.
- JKS is requested explicitly by the user and is accepted by Android build tooling.
- Secrets are written at repository level; environment-level and organization-level secrets are
  out of scope for this feature.
- Storing results in the KeePass database is done by the caller (plugin integration layer); this
  feature defines what data is handed back, not the database entry layout.
